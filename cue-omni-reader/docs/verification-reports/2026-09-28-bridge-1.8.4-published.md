## What changed

Bridge 1.8.4 is not only a pin sync: it carries one behavior fix for local-file non-text parsing. The tool surface is unchanged from 1.8.3.

- **Version and trust-set sync.** `package.json` / `package-lock.json` / `BRIDGE_RELEASE_VERSION` move to `1.8.4`; the trusted managed-entry pair advances to **1.8.3 / 1.8.4** (`PREVIOUS_RELEASE_VERSION=1.8.3`); a `1.8.2` entry is no longer a trusted managed entry, and `setup` fail-closes on it before any health check or config mutation rather than upgrading it in place — the same hard cut 1.8.3 had already applied to 1.8.1. The only bare-`npx` Windows migration exception remains 1.5.1.
- **Local `grounded`/`layout` preflight now resolves the same advertisement as the grant.** The tool-level preflight for a local-file non-text request read its direct profile from the v1 capabilities advertisement (`/api/omni-reader/capabilities/v1`) alone. The Cube origin has never served v1 — only `/capabilities/v2` is registered — and a 404 on that read maps to `DETAIL_CAPABILITIES_UNAVAILABLE` ("This Omni service does not advertise grounded or layout parsing."). So every local `parse(detail=grounded|layout)` failed closed even though the served v2 advertisement lists both details and `createGrant` already negotiated v2 → the v4 grant body. The preflight and the grant had diverged since v2 was added (the fix records 2026-09-01).
- **One resolution, shared.** Both now go through a single `CubeGrantClient.resolveDirectProfile`: v2 decides; the legacy v1 advertisement is consulted only when v2 is absent (a 404, which is not cached), and only for a non-text detail (text keeps its profile-less legacy grant body). `OmniToolDependencies` exposes only `createGrant` and `resolveDirectProfile`, so a separate v1-only read cannot be reintroduced.
- No change to remote URL `grounded`/`layout` (1.8.2), the tool surface, URL capability negotiation, or bundle recovery.
