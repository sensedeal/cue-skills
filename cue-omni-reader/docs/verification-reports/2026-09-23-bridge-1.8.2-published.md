## What changed

Bridge 1.8.2 keeps the frozen seven-tool surface. It completes the remote URL `grounded`/`layout` path that 1.8.1 prepared on the client side.

- **Capability negotiation reaches the live service.** Before a non-text `parse`, the Bridge sends `initialize` and reads only `capabilities.experimental["cue.omni-reader"]`. 1.8.1 sent that request with `accept: application/json` only. The Cube MCP streamable-HTTP transport requires both `application/json` and `text/event-stream`, so it answered 406. The Bridge mapped that to `REMOTE_REQUEST_REJECTED`, and every remote non-text parse failed at negotiation: no operation, not billed. 1.8.2 accepts both types and decodes an SSE reply, the same way `tools/call` already did. A broken response stream is still a `REMOTE_PROTOCOL_ERROR`.
- **A completed bundle is recovered locally by a later process.** 1.8.1 never recorded a remote bundle's local result id. Separately, the local artifact store never implemented bundle-descriptor recovery. So when a new Bridge process repeated an identical grounded parse inside the delivery window, it refetched a result the service had already delivered and acknowledged, and got a retryable `SERVICE_TEMPORARILY_UNAVAILABLE`. 1.8.2 records the bundle's result id and rebuilds the descriptor from the durable local manifest. The same recovery applies to a local-file grounded result.
- `detail=text` and omitted `detail` are unchanged. `read_outline` still reads flat Markdown results only.
- The trusted managed-entry pair advances to 1.8.1/1.8.2; the only bare-`npx` Windows migration exception remains 1.5.1.
