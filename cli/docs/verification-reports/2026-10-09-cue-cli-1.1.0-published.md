## What changed

`@cueai/cue-cli` is the local CLI bridge for cuecue.cn deep research: device-flow login, playbook lookup, and streaming research runs that deliver cited Markdown reports. 1.1.0 is the version the WorkBuddy connector package declares as its floor.

- **Device-code authorization (RFC 8628) replaces the earlier token-only form.** `cue auth login` prints a `verification_uri` carrying `user_code=XXXX-XXXX`, polls `/cli/device/token`, and treats the spec's `authorization_pending` (HTTP 400) as "keep polling". `auth status` decides locally from the credential store and returns 0/2; `auth logout` calls the revocation endpoint and the family dies immediately.
- **Two endpoint families, two prefixes (one base cannot serve both).** Authentication endpoints sit under `/{sso}/api` (`/cli/*`, `/oauth/*`, `/.well-known/*`) while research/business endpoints sit under the host root `/api` (`/templates`, `/chat/stream`, `/tools/capabilities`). `cli/src/bases.ts` resolves both from the single configured base and routes per endpoint; `doctor` probes one endpoint of each family and reports `bases:{auth,business}` plus `cliVersion`.
- **Credentials persist across process and host-app restarts.** Access/refresh tokens land in `~/.cue/credentials.json`; a 401 triggers exactly one silent refresh before surfacing an error.
- **The connector package** (`cli/connector/`: `cli.json`, `connector-meta.json`, `icon.svg`, and `cli/skills/cue-research-cli/SKILL.md`) is the artifact handed to WorkBuddy. `cli.json` declares `versionCheck.minVersion = 1.1.0`, `init` = `npm install -g @cueai/cue-cli` for darwin/linux/win32, `auth`/`unAuth`/`status` commands, `statusMatch`, and `authDeviceFlow` with `authWaitForExit: true`.
- **`minVersion: 1.1.0` is why this publication was a hard prerequisite:** with only 1.0.0 on the registry, a real user's `init` installs 1.0.0 and the connector fails the version gate ("CLI 版本过低（1.0.0 < 1.1.0）") — the failure observed on a real WorkBuddy host.

## Boundaries

- **No credentials are recorded here.** No npm token value, access/refresh token, authorization header, or account secret appears in this report or in the published package.
- **The publication used a granular access token that bypasses 2FA, supplied by the owner.** npm currently blocks such tokens from *account changes* (already in effect) while *direct publishing* remains permitted until its stated 2027-01 date. The consequences are recorded below because they affect future releases of this package: (a) publishing with this token class will stop working at that date; (b) the token could not delete a `dist-tags` entry — every DELETE returned `403 Granular access tokens that bypass two-factor authentication may not perform this action`.
- **Two diagnostic `dist-tags` entries were created during the publication and were removed on 2026-10-10.** To establish package-level write permission before publishing, the agent issued reversible `dist-tag` probes. The creation succeeded but the compensating deletion was refused at publication time, leaving `wf-probe-tmp → 1.0.0` on `@cueai/cue-cli` and on `@cueai/omni-reader-mcp`. Neither tag was ever referenced by package metadata, and **both have since been removed**; each package now carries `latest` only (`1.1.0` and `1.8.6` respectively), with no package version or tarball affected. The removal is worth recording because of *how* it had to be done: the maintainer account's second factor is a **security key, not a TOTP authenticator**, so no one-time password exists to pass to `--otp`. In a non-interactive shell every attempt returns a flat `403` or an `EOTP` demanding the missing code — npm never starts a challenge. The deletion only succeeded when the same command ran in a **real TTY**, where npm prints `Authenticate your account at: https://www.npmjs.com/auth/cli/...` and completes the 2FA challenge in a browser, which is where a security key can be used.
- **Package-level maintainership is the gate, not organization role.** `@cueai/cue-cli` carried a single maintainer (`huhoo`) while `1k-npm` held the organization owner role; `PUT` returned `404` in that state and `204` once `1k-npm` and `wangxiaoxu2008` were added to the package's maintainers. Organization roles (admin as well as owner) did not grant publish permission on this package.
- This report covers publication and registry state only. The WorkBuddy connector submission itself, the production deployment, and the cross-platform (Linux) verification are separate steps and are tracked on the map, not claimed complete here.
